# 电池管理深度审查（2026-09-27）

## 结论与范围

按本次要求“开启管理后，电量高于目标应主动放电到目标”，当前实现不满足要求。项目有真实 SMC 控制、回读和恢复机制，但策略、命令同步和界面语义没有形成可靠闭环。

审查对象是当前工作区，包括未提交修改。未修改产品代码，未安装或执行特权控制工具，未对真实电池进行充放电操作。结论来自源码追踪、现有测试及提取生产控制器方法的隔离复现；真实机型的 SMC 写入效果和物理响应时间仍需实机验证。

## P1：应优先修复

### 1. 启动管理不会主动降到管理电量

位置：`Sources/batteryctl/policy.h:14–18`。

例如电量 95%、目标 80%，点击“启动管理”发送 BAT_LIMIT；策略返回 POWER_HOLD，仅禁止充电并保留适配器输入。只有 BAT_DISCHARGE 才断开适配器输入，让电池供电。因此接电后电量可能长时间保持在 95%，无法达到用户要求的 80%。降低管理上限也有同样问题。

建议：管理模式在具备主动放电能力、接电、开盖时，对高于目标的电量主动放电；到目标后恢复适配器直供，低于恢复阈值再允许充电。不支持主动放电时明确显示“仅限充，无法主动降到目标”。合盖、休眠、未接电时保留明确的保护规则。

### 2. “充电”按钮实际会禁止充电

位置：`Sources/ClaudeBar/Models/BatteryChargeController.swift:18–34`；`Sources/batteryctl/policy.h:13–14`。

UI 将 `.hold` 标为“充电”，提示“充电到上限后保持”，注释也认为 BAT_HOLD 会充电。但 C 策略对所有 >=20% 的电量直接返回 POWER_HOLD。电量 50%、上限 80% 时点击“充电”，实际会停充，状态文字随后显示“已暂停充电”。只有低于 20% 才被保底分支放行。

建议：先落实按钮语义，再统一 UI、枚举、策略和测试。如果保留“充电”，应充到目标再保持；如果保留原有 BAT_HOLD 行为，必须标为“暂停充电”。现有 C 测试明确断言 BAT_HOLD 在 >=20% 时保持停充，所以测试通过不能证明按钮正确。

### 3. 滑杆会覆盖尚未确认的模式切换，包含“还原系统”

位置：`Sources/ClaudeBar/Models/BatteryChargeController.swift:195–203`；`Sources/ClaudeBar/Views/Shared/BatteryChargeControls.swift:65–74`。

`apply()` 设置 pending，但滑杆没有禁用，`setLimit()` 也不检查 pending，且使用最后确认的旧 `mode` 发完整命令。

隔离复现：原模式为 limit，点击“放电”后马上拖动，依次发送 `set 3 80 1`、`set 1 70 2`，最后回到 limit。点击“还原系统”也会产生 `set 0 80 1`、`set 1 70 2`。辅助进程先排空输入，再执行最后一个命令；若两条命令在同轮读取，恢复系统的请求会被覆盖。若系统恢复已执行，则后续命令又可能落入正在退出的进程。

建议：统一管理“期望模式、期望阈值、已确认状态”。排队或合并操作时保留最新用户意图，尤其不能让调阈值隐式取消恢复系统。仅丢弃忙碌期间的滑杆请求也不够，否则界面已变、实际未变。

### 4. 快速把上限拖回原值，会丢失最后一次设置

位置：`Sources/ClaudeBar/Models/BatteryChargeController.swift:198`。

隔离复现：已确认上限 80%，先拖到 60% 并松手，在回执前再拖回 80%。第二次因为 `target == appliedLimit` 被跳过。最终只有 60% 命令发出，界面主数值和保存值是 80%，实际上限是 60%。控制器收到回执也不会修正 `threshold`。

建议：去重应比较最新期望值/在途值，而不是仅比较旧回执值；有在途请求时，恢复到旧值仍需发送或排队。界面区分“目标值”和“已生效值”。

## P2：同步、恢复和交互缺陷

### 5. 阈值修改没有响应超时，失联后仍显示可管理

位置：`Sources/ClaudeBar/Models/BatteryChargeController.swift:183–203, 237–249, 298–307`。

只有 `apply()` 启动 8 秒响应超时。`setLimit()` 不设置 pending、不等待确认、不启动超时；日常运行也没有最后一次有效状态的时间戳或接收超时。辅助进程停止回报但仍存活时，旧状态会一直显示。

另外 `managesLimit` 只检查 process 和 mode。超时/写入失败已关闭 input、等待子进程恢复时，它仍为 true，UI 继续显示勾号及“松手即生效”。此时 `input?.write` 对 nil 静默跳过。隔离测试确认了这两条路径。

建议：所有写操作都需要确认和超时；单独跟踪连接健康和回执新鲜度；恢复中或断开时不得继续宣称阈值已经生效。

### 6. 首次启用/授权期间改变上限，实际执行的是点击时的旧值

位置：`Sources/ClaudeBar/Models/BatteryChargeController.swift:217–230`。

`apply()` 在授权之前把 threshold 捕获到局部 target。系统授权期间滑杆仍可操作；由于 helper 尚未启动，滑杆松手不会发命令。授权结束后仍发送旧 target。例如点击时 80%，等待输入密码时改成 60%，最终实际启用 80%，界面保留 60%。

建议：授权后读取最新期望状态，并在确认前后处理授权期间的修改；或者明确禁用滑杆并解释正在应用哪个值。

### 7. 自动恢复依赖控制面板出现，授权完成后不会续接恢复

位置：`Sources/ClaudeBar/Views/Shared/BatteryChargeControls.swift:45`；`Sources/ClaudeBar/Models/BatteryChargeController.swift:96–123, 142–174`。

`probe()` 的调用入口只有控制视图的 onAppear；应用启动路径没有主动初始化电池管理。概览使用 LazyVStack，电池控件未出现时恢复可能被推迟，无法保证“应用启动即恢复管理”。

若探测时辅助工具未安装或已过期，`resumeStarted` 先被置为 true，随后退出。用户去设置页完成授权后，`authorizeHelper()` 只更新授权状态，不再执行恢复。此时旧 mode 仍可被选中，statusText 会因为 helperInstalled=true 显示“正在恢复上次的充电管理…”，实际没有恢复任务。

建议：由应用生命周期触发一次恢复；明确区分“上次偏好”和“本次已确认模式”；安装成功后续接待恢复意图，失败可重试，不能只改变文案。

### 8. 控制确认与能源读数来自独立时间线

位置：`Sources/ClaudeBar/Models/BatteryChargeController.swift:48–56, 310–323`；`Sources/ClaudeBar/Utils/ProcessSampler.swift:333–359, 395–427`。

辅助进程每 2 秒评估并回报 percent，但控制器不使用这个 percent；能源图和菜单电量取另一个 ProcessSampler 的读数。采样档位为：前台活跃 1 秒、前台有监控范围且空闲 2 秒、后台有范围 6 秒、无范围但有可见窗口 6/12 秒，无消费者时暂停。

控制写入确认后没有触发立即采样，没有共同时间戳，也没有“指令已应用，等待传感器确认”的状态。于是下面已经显示停充/放电，上面短时间仍显示充电是可发生的；不能把这种 UI 差异直接解释成硬件指令失败。SMC 回读一致也不等于电流已按预期变化。

建议：保留控制状态和测量状态各自含义，携带采样时间；命令确认后主动请求一次电池读数，并在有限时间内核对电源状态/电流方向，过渡期明确显示正在确认。物理变化不应伪装成零延迟。

### 9. 成功回报不清除旧错误

位置：`Sources/ClaudeBar/Models/BatteryChargeController.swift:310–323`。

例如未接电点击“放电”收到 adapter_required，自动回到 limit；之后持续收到无错误状态，`lastError` 仍保留，设置页与控制面板继续展示旧失败。隔离测试已复现。过期 revision 的错误还会在版本过滤前写入 lastError。

建议：区分当前状态错误和需要保留的恢复失败告警。匹配当前请求的成功确认应清理已解除的普通错误；旧回执不得污染新操作。不能无条件清除尚未确认恢复的硬件失败。

### 10. 能源图会把主动控制解释成错误原因

位置：`Sources/ClaudeBar/Views/Shared/PowerFlowCard.swift:116–127`。

holding 固定解释为“已充满或优化充电暂停”，遗漏本工具主动限充；onBattery 固定解释为“未接电源”，没有区分主动断开适配器输入；assisting 固定归因“电源只能提供…”，也不是功率读数单独能证明的原因。

建议：根据确认的控制状态补充原因；无法确认原因时仅描述观测到的能量流向。此处数据可能正确，解释却不正确。

## 延迟与生命周期

- 普通命令收到后将 lastTick 清零；helper 每轮最多运行 0.25 秒的 CFRunLoop，因此健康空闲条件下不是固定等待 2 秒才应用，而是约下一次 250ms 循环检查加硬件调用时间。该数字是代码调度量级，不是实测 SLA。
- 首次开启包含安装校验和管理员交互。已安装时仍有多次 codesign 校验；代码无法给出固定耗时。8 秒超时从启动并发命令后计算，不包含用户授权等待。
- 无新命令时电量变化、合盖判断按 2 秒策略周期处理。
- 休眠前恢复原始控制，主动放电切回 limit；休眠期间不维持上限。唤醒后回到策略循环。当前 hold 模式并不会统一变成 limit，技术文档“唤醒恢复限充”的说法过于宽泛。
- UI 心跳使用默认 RunLoop 的 Timer，缺少跟踪模式下的可靠性验证；helper 在 20 秒无心跳时恢复并退出。建议专门测试长时间菜单跟踪/拖动和主线程卡顿，不能仅凭正常点击验证稳定性。
- 正常退出以 stdin EOF 触发恢复，不等待物理效果确认。终态上报为 mode=system，receive 对无错误状态无条件保存 mode；若退出阶段仍处理到该回报，会把用户的管理偏好写成 system。此项属于条件性生命周期风险，应通过终止集成测试确认是否可达，并从设计上分离“退出清理状态”和“用户持久偏好”。

## 已有实现中合理的部分

- 阈值统一限制 20–100%，默认 80%；limit 模式有 2 个百分点滞回，低电量保底允许充电。
- SMC 写后回读、有限重试、恢复时先连接适配器再恢复充电。
- 对启动时的已有控制值拒绝接管；用进程锁避免多实例争用。
- EOF、心跳超时、读电池失败和信号退出有恢复路径；休眠有专门处理。
- 模式操作原则上等待 helper 回执后更新实际状态；generation 防止旧进程消息污染新进程。
- 未启动管理时拖动只保存偏好，避免滑杆隐式拉起管理员授权。

这些机制说明底层具备真实控制能力，但不能证明本机/所有支持机型的硬件效果，也不能抵消上面的产品和同步问题。

## 验证结果与缺口

1. `Tests/battery-control.c`：以 `-Wall -Wextra -Werror` 编译并通过；SMC transport 为内存模拟。覆盖策略、回读、回滚、休眠等已有断言。
2. `Tests/charge-limit-regressions.py`：通过，验证单次滑杆门控、范围和退出禁止发送。
3. 临时隔离脚本 `/tmp/claudebar-battery-audit.py`：提取当前完整 Swift 控制器，开放可见性以设置测试状态，将发送与安装依赖替换为内存桩，并使用独立 UserDefaults suite。实际执行生产 apply/setLimit/receive 方法，复现阈值回拖丢失、模式被覆盖、阈值无超时、错误不清理、断开仍标可管理，以及回执不协调显示值。未启动 helper。
4. 现有测试缺少交互序列和控制器与 helper 的协议集成测试；`make test` 也未包含 C 电池测试。此次既有测试通过，并不代表完整产品行为通过。

建议修复后至少验证：95%→管理80%、50%→充电80%、80→60→80快速调节、还原系统并拖动、授权期间改值、授权后恢复、拔插电源、合盖/休眠/唤醒、helper失联/错误恢复，以及两个入口同时操作。最后再在目标机型上记录命令、回执、电流方向与时间戳，确认实际充放电闭环。
