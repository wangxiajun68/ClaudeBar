# 架构演进与品牌升级评估

日期：2026-10-15。状态：提案，未实施迁移或正式改名。

后续深入评估见[桌面架构深入调研与选型方案](desktop-architecture-selection-2026-10-15.md)，补充了 GPU 原生路线、发布版本核对、视觉技术栈与原型验收。

目标：功能持续扩展、视觉升级和性能同时考虑。这里将“扩展”理解为模块扩展，并为未来跨平台预留边界；Windows / Linux 的交付范围尚未确定。

## 建议

长期评估方向是 **Rust 业务核心 + React / TypeScript 工作台 + 必要的 Swift / AppKit 平台层**。跨平台成为交付目标时，优先验证 Tauri 作为桌面宿主。迁移按模块进行，每一步保留可交付的 macOS 应用。

近期先保留现有原生宿主，用一个只读工作台页面验证 Web 界面的收益；再用独立业务模块验证 Rust。不要把宿主替换、所有页面重写、核心重写、数据迁移和品牌身份修改放进同一版本。

这是一条待验证的工程路线，不是性能结论。Swift 本身并非当前已证明的瓶颈；React 和 Rust 都不会自动消除过量刷新、全量解析、重复查询或无效动画。

产品已覆盖模型与供应商、协议转换与网关、会话监控与迁移、用量与请求记录、VPN、连接器与飞书文档、硬件状态与控制、截图、菜单栏、灵动岛、Widget 和 CLI。ClaudeBar 的名称已不能准确表达范围。

重要实现边界：

- `CodexProxyServer` 使用 Network / NWListener；`VpnManager` 管理 mihomo 与系统网络集成。
- 菜单栏与灵动岛使用 AppKit 面板；截图依赖 ScreenCaptureKit；硬件能力涉及 IOKit 与现有 C 辅助工具；Widget 使用 WidgetKit。
- `FeishuOfficialDocumentView` 已经使用 WKWebView，说明仓库已有局部混合界面的实践，但其专用桥接不能直接扩大为通用系统控制接口。
- CLI 已有 `mtx` / `mtx-dev` 短命令和 Matrix 定位，现有业务与快照契约应复用。
- 当前性能策略包含后台解析、增量索引、可见性调度、字段级发布与取消。迁移必须保留这些行为，详见[当前性能文档](../technical/08-performance.md)。

## 技术职责与方案比较

Rust、Go 是语言，Node.js 是运行时，React 是 UI 库，Three.js 是 3D 图形库。它们处于不同层，不需要全部加入产品。

| 技术 / 路线 | 对本项目的用途 | 主要代价 | 判断 |
| --- | --- | --- | --- |
| 继续 Swift 并按业务拆分 | 保留原生体验，先解决模块边界 | Web 组件生态和跨平台复用较少 | 必须作为基线与迁移对照 |
| Swift 宿主 + React / TypeScript | 复杂列表、分析、配置和文档工作台 | 增加 Web 渲染与桥接成本 | 近期首个验证方向 |
| Rust 核心 + Tauri + React | 可复用核心与跨平台桌面工作台 | 移植、IPC、构建签名与原生桥接均需维护 | 长期优先评估方向 |
| Go + Wails + React | 网络服务、文件扫描、协议处理与 Web UI | 原生能力仍需平台适配，Go 运行时也需计入测量 | 团队更熟悉 Go 时的替代方案 |
| Electron + React / TypeScript | Web 生态、Chromium 一致性、Node 集成 | Chromium / Node 分发与多进程资源预算 | 有明确 Chromium / Node 需求时再选 |
| Three.js | 可选的拓扑、空间关系和专门的 3D 展示 | GPU、渲染循环、可访问性和降级成本 | 按具体场景引入 |

[Tauri 官方进程模型](https://v2.tauri.app/concept/process-model/)说明其核心使用 Rust，UI 使用系统 WebView；macOS 对应 WKWebView。因此其平台 Web 能力仍需按 macOS 15 基线验证，不能以 Chrome 开发预览代替。

[Wails 官方架构](https://wails.io/docs/howdoesitwork/)采用 Go 应用与 Web 前端的绑定方式；[Electron 官方进程模型](https://www.electronjs.org/docs/latest/tutorial/process-model)说明其 Chromium 多进程模型与 Node 环境。以上是架构事实，不能直接推出本项目的实际内存、能耗或速度排名。

[React 支持增量接入已有项目](https://react.dev/learn/add-react-to-an-existing-project)，适合先迁一个页面。[Three.js](https://threejs.org/)的职责是 3D 图形，不能替代宿主、权限、业务状态或存储层。

建议只选择 Rust 或 Go 中的一种新核心语言。已有 mihomo 继续作为归档随包使用，无需因选择 Rust 而重写。Node.js 初期仅用于前端构建，生产工作台加载编译后的静态资源，不额外要求常驻 Node 服务。

## 目标边界

```text
React / TypeScript 工作台
  会话、模型、用量、流量、连接器、文档、设置
             │ 版本化命令 / 查询 / 事件
             ▼
可复用业务核心（逐步评估迁入 Rust）
  解析与索引、路由与协议转换、用量聚合、模块状态
             │ 窄范围平台接口
             ▼
macOS 平台层（保留 Swift / AppKit 与现有辅助工具）
  菜单栏、灵动岛、Widget、权限、截图、系统网络、硬件
```

过渡期原生宿主继续拥有生命周期；若最终采用 Tauri，由它统一承担宿主职责，避免再保留一个拥有相同职责的完整 Swift 主应用。Swift 平台能力按需要嵌入或桥接，Widget 仍是独立的原生扩展。

业务拆成有明确责任的模块即可，不拆成本机微服务集群，不引入常驻构建服务。先用进程内边界；只有生命周期或故障隔离需求成立时才考虑子进程。跨进程后必须明确启动、取消、退出与恢复的所有者。

边界契约：

- 查询读取分页或有界快照，事件合并批量推送；避免每个 Token 或硬件采样都使整页更新。
- 前端使用不含密钥的展示模型。已有凭据留在受控核心，编辑密钥的输入只经过专用写入接口，不进入通用快照、事件、日志或浏览器持久存储。
- 桥接只暴露明确命令，做参数、来源与权限检查；远程文档内容不获得本地系统能力。Tauri 的[能力机制](https://v2.tauri.app/security/capabilities/)是宿主权限的一部分，不能替代业务入口的 dev 限制。
- 每份可变数据同一时间只有一个写入者；迁移期间不允许两套核心同时写数据库、管理 VPN 或操作辅助工具。
- Swift 与新核心分别在真实副作用入口执行编译期 dev / release 策略，不能依赖前端隐藏按钮，也不能允许环境变量解除限制。
- 组件扩展优先使用明确接口和适配器；当前没有必要设计可执行任意脚本的插件系统。

## 分阶段交付

| 阶段 | 具体产出 | 继续条件 |
| --- | --- | --- |
| 0：基线与边界 | 模块清单、只读合成数据、当前优化构建的性能基线 | 相同数据、窗口、显示器与场景可以重复对照 |
| 1：品牌解耦 | 展示名与数据目录、bundle、App Group 等技术身份分开 | 配置与凭据位置不变，dev / release 隔离回归通过 |
| 2：Web 页面试迁 | 现有 dev 宿主中的只读用量页，含图表、日期筛选、大列表和明暗外观 | 视觉目标达成，核心场景符合约定的资源与交互预算 |
| 3：Rust 模块试迁 | 从纯协议转换 / 流式解析等边界清晰的模块中选一项 | 与 Swift 结果一致，分块、取消、错误和资源上限有回归 |
| 4：扩展工作台 | 按收益扩展页面和核心模块；明确 Windows / Linux 功能矩阵 | 每个模块有唯一状态与写入所有者，可回退 |
| 5：宿主决策 | 需要跨平台时验证 Tauri、Swift 桥接、Widget 打包和签名 | 多显示器、失焦、唤醒、快捷键及生命周期满足产品要求 |

阶段 2、3 分别回答“Web UI 是否值得”和“新核心是否值得”。任一方向没有收益，就保留该部分已有实现。不要在试迁结果出来前承诺全量重写日程。

性能验收使用全部相关进程的总成本，包括 WebContent、GPU 与子进程，避免只看宿主 RSS。覆盖冷 / 热启动、工作台可见静止、完全隐藏、滚动、典型业务请求，以及长时间运行。

先取得基线再确定数值预算：CPU / GPU、物理内存与峰值、唤醒与能耗、交互延迟、帧间隔和长帧、解析吞吐与取消延迟。纯函数微基准不能代替整机交互验证；实验数据不能写成已交付的性能提升。

Three.js 仅在信息表达确有收益时使用。静态图表、流程图和常规后台页面优先使用普通 DOM / SVG / Canvas；3D 场景按需加载，在隐藏、屏外和减少动态效果时停止或降级。保留现有 Metal 天气渲染作为可比较的实现。

## 品牌方向

建议定位：**面向 AI 开发的本地工作台**。主品牌不绑定某个模型供应商，也不绑定菜单栏这一种界面；VPN 和硬件能力作为工作环境模块，不挤进主品牌名。

优先候选：**Lattio · 枢台**。英文取网格、连接和工作空间的联想；中文表达集中管理工作状态与能力的工作台。它是命名提案，不表示已经采用，也不表示域名或商标可用。

备选方向：

- **枢台**：中文为主，功能范围清楚，适合强调本地工作台。
- **Matrix**：与已有 `mtx` CLI 连贯，但已有知名的 [Matrix 通信生态](https://matrix.org/)，直接作为公开主品牌容易产生搜索和认知混淆。

本次有限公开检索未发现 Lattio 的明显同类软件结果，但发现同名灯具；这不足以确认名称可用。定名前再核对目标分发渠道、代码仓库、域名与相关名称。不要仅因搜索未命中就声称“没有重名”。

品牌可以先升级，技术身份单独处理：

1. 先引入用于界面与分发文案的展示名，保留既有稳定存储身份。
2. `FilePaths.appSupportDir` 当前通过 `BuildChannel.appName` 拼接路径；因此不能直接全局替换该字段来改名。后续应明确独立的数据目录字段，并保留正式版现有路径。
3. 按仓库规范，正式版继续保留 `com.claudebar.app`、既有 App Group 与数据路径；保留旧 URL scheme / CLI 兼容入口，新增入口另行设计。
4. 同步调整应用名、Dock / 菜单文案、图标、Widget 展示名、帮助、README 和发布产物。打包与签名校验、安装路径识别、CLI 启动识别必须同步验证。
5. 目录、命名空间和兼容文件名不必与品牌同步重命名；后续确需调整时单独迁移，不复制真实凭据到 dev。
